# SQLite 权威状态与 IPFS RunHistory 辅助归档：架构评估

本文件支持 [Implementation](Implementation.md)。2026-11-14 用户进一步订正：SQLite 是真正的权威信息源，IPFS Store 只是辅助存储；允许记录存在但历史详情已经失去保留或不可取得。当前方案以此为准，取代此前的 DAG 事实源与可丢弃查询 SQLite 方案。实施顺序见[分阶段计划](RefactorPlan.md)，待讨论边界见[待决定项](ideal/OpenQuestions.md)。

## 已确认的责任边界

| 部分 | 职责 |
| --- | --- |
| SQLite | 请求、准入、运行状态、消息处理、幂等、期限、记录保留及归档管理的权威事实与查询 |
| IPFS RunHistory DAG | 保存已定稿的运行历史及其强引用详情，作为辅助归档，不决定运行状态或是否过期 |
| Store pin 协调 | 执行保留/释放意图、保护临时内容与其他 owner，不决定业务生命周期 |

- 未执行、执行中的 Task/Run 状态继续在 SQLite 中保存，不逐次生成权威 RunHistory head。
- 执行历史以 RunHistory 为单位，Task 仍为请求与匹配/查询投影；多个 Task 可以关联同一 Run。
- SQLite 记录、详情保留资格、Store pin 及当前可读性是不同维度。记录存在不保证详情可读；unpin 不等于块立即消失。
- Task 或记录是否过期，由 SQLite 中的事实和策略决定；IPFS 内容存在不能恢复已删除记录，内容缺失不能倒推 Task 已过期。
- SQLite 不再是可以从 RunHistory 完整重建的缓存。恢复业务需要 SQLite 的权威备份；只有仍需保留的归档详情另备份对应 DAG/Store 元数据。
- Payload 引用仍是强引用。写出并声称完整的归档必须具备可验证闭包；之后合法释放保留或内容丢失，并不会把编码改成弱引用，只会使该归档当前不可完整取得。

用户说“不把尚未执行或执行中的 Task 存入 IPFS”，明确取消的是活动状态/history 的持续归档。本次不据此取消之前确认的 CID 输入资源访问、临时内容写入或运行时依赖保护；资源内容与活动状态记录须分开。若要禁止运行中一切 IPFS I/O，则属于另一个改变现有能力的决定。

## 旧风险的处理结果

### R-01: 提交权威已经明确

SQLite 是业务提交权威，不再建立一个取代它的 IPFS 数据域 head。历史归档 CID 与写入/保留/清理意图记入 SQLite；Store 自身可保留必要 pin 协调元数据，但不能成为另一套业务状态源。

此前 R-01 “仅少量协调 SQLite 耐久、查询 SQLite 可丢弃”的方案由本次订正取代。数据库物理划分属于实施细节，不要求为了延续旧方案强制拆成权威 registry 与非权威业务库。

### R-02: Run 前事实与保留以 SQLite 为准

未产生 Run 的请求、准入下界、幂等窗口及跨 Run 顺序仍保存在 SQLite，无需为它们设计独立 IPFS 恢复根或全域 manifest。

允许 SQLite 的记录保留期长于 IPFS 详情保留期。何时请求 unpin、是否还能展示结果摘要、何时删除记录，各按 SQLite 策略执行，不隐含永久保留。详情释放后，幂等事实仍可保留，不能把同一旧请求重新接纳执行。

业务摘要、可恢复执行所需数据与可回收详情的字段边界需在实现中列明，不能在运行仍需要它们时提前删掉 SQLite 数据。

### R-03: 原准入悖论消除，归档完成边界仍需确认

preparing/拒绝/依赖取得失败可以直接作为 SQLite 事实保存，不再要求先构造一个完整 DAG 才能记录请求。仍不能将未验证或不可访问的必要资源投递给 Worker，也不能把不完整归档声称为成功。

真正剩余的行为选择：

1. Run 在什么稳定边界形成 RunHistory：不能仅看到 outcome 就忽略后续 exit、清理证明或未知资源释放。定义内容定稿点，不能把仍在变化的执行历史提前当作最终归档。
2. 归档失败是否阻止业务完成确认。推荐运行结果按 SQLite 已提交事实成立，归档单独记录待处理/失败并可重试，不把辅助存储失败改写成重新执行；但“允许后来详情丢失”不自动等于用户已接受首次归档可失败而完成。
3. IPFS 辅助历史与运行期间的 CID 资源存储分层；若资源输入/临时写入也要求移出 IPFS，须另行决定，不能静默删除 context 能力。

这些推荐不作为已确认行为。归档定稿和首次归档成功条件是下一轮优先讨论项。

### R-04: 私有归档边界仍待确认

完成后的 RunHistory 仍可能包含私有参数、消息、调用方及执行证据。Engine 的 SQLite/HTTP 授权不会自动保护另一入口上的 Kubo/网关块读取。

推荐私有受控 Store，不自动公开 RunHistory 根；公开交付子图单独授权导出。若要求公网上存放可读取的核心历史，则须明确加密/密钥/共享边界，而不是把 CID 当访问令牌。该问题并未因 Store 变为辅助存储而消失。

## D-01: JSON 与强链接归档转换

```text
SQLite 中已定稿的历史与 IpfsPayload 描述符
  → 验证 data/cidPaths、恢复真实 CID
  → 规范 DAG-CBOR 编码结构化节点
  → 写入并验证强链接闭包
  → 按 SQLite 归档意图 pin
  → SQLite 记录已确认的归档结果
```

- DAG-CBOR 是本次规划的结构化编码方案，raw/UnixFS 继续用于资源。宿主归档编解码不扩成 Worker 文件/目录 DU 的第三种伪文件。
- ipfs-payload 只负责转换/编码，ipfs-store 负责块、闭包与 pin，SQLite/Engine 决定业务状态与保留策略。
- 固定字节/CID 测试向量，使用真 IPLD 链接，覆盖 DAG-CBOR/DAG-PB/raw 混合闭包；同形普通业务对象与字符串不误转换。
- 编码成功不证明目标完整，pin 不代表 SQLite 已发布归档。导出整份历史必须重新验证当前闭包，不能仅凭曾经成功的标记。
- 规范依据：[IPLD DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/)的 CID tag 42、字符串 map key 与规范编码。

## D-02: cidPaths 是受约束的定位规则不是可执行查询脚本

- 使用属性、固定下标、通配符和字面量 discriminator 的受限 JSONPath AST，不执行任意 JS、递归查询或用户函数。
- 依据 Schema 与实际分支求具体位置，校验位置集合一致；不能漏标、多标、猜测 CID 字符串，复杂规则安全回退具体位置。
- 可选字段和空数组允许零匹配，不掩盖 required 缺失；限制路径数量、长度、深度及求值节点数，越限明确失败。
- DAG 真链接与保留的标注必须一致；导出时重新生成或校验 cidPaths，而非信任第二套相互矛盾的引用信息。

## D-03: 归档与清理需要可恢复意图，不需要新业务事实源

归档建议采用 SQLite 耐久意图配合幂等 I/O，以下顺序不提前决定 R-03 的业务完成确认策略：

| 边界 | 故障后的要求 |
| --- | --- |
| 已记归档意图，写块未完成 | 从 SQLite 恢复归档工作，不重新执行 Run；未完成归档不冒充可读 |
| pin 生效但 RPC 返回失败 | 保留可查证的意图并幂等恢复，不擅自解除外部 pin |
| pin 成功，SQLite 尚未确认 | 候选暂受保护；复核运行归档/保留代次后完成或回收 |
| SQLite 已撤销保留，旧归档任务迟到 | 旧任务不能重新发布可用归档或复活已过期记录；使用代次/条件更新 |
| unpin 后进程退出 | 重试清理意图；记录是否存在和是否过期仍以 SQLite 为准 |
| 历史块被 GC/缺失/损坏 | 列表与状态查询按 SQLite 返回；详情明确报告缺失/损坏，不能返回空历史伪装成功 |
| SQLite 丢失 | 从权威数据库备份恢复，不扫描 IPFS 重新创建请求/Run/幂等事实 |

Store 多 owner 和临时保护仍需保留。对本 owner 执行 unpin 不得破坏别的运行或外部应用对同一块的保护。结构化历史写入可以异步，但不能把所有同步 SQLite 事务强行迁移为网络事务。

## D-04: 记录状态、保留意图与可读性分离

- 至少区分业务完成/过期、归档是否生成、保留是否已释放、最近实际读取的结果；具体字段名待实施设计，不能只用一个 completed 或 available 覆盖所有状态。
- 未观察当前存储不能断言可读；网络暂不可达也不等于已经永久丢失。明确区分暂时访问错误、缺失、损坏、尚未归档与未授权。
- unpin 后块可能尚在，也可能仍被其他根保留；不能立即写成“内容已物理删除”。是否允许继续尽力读取由 SQLite 权限与保留策略决定。
- 内容缺失不回滚既有结果，也不启动 Worker 重建详情；需要历史内容时只能明确报告缺失或从有授权的备份恢复。
- RunHistory 按运行定稿，不无限串联不同 Run 的历史根；以段/页保持块尺寸受限，保留期内完整强闭包与后续释放不冲突。

## D-05: 不变的实施约束

- 不迭代已有 Schema/API 版本，直接更新当前内部协议；不改写旧制品，不自动删除或迁移旧数据库。
- SQLite 是必要备份，IPFS 仅备份仍需恢复的历史与资源；详情已合法丢失时数据库恢复不承诺找回它。
- 不保留旧 input/Space 协议兼容层；三个通道、文件/目录 DU、raw/UnixFS、按需 ipfs-tree 与完整单测继续有效。
- 宿主凭据不写入归档；日志与生命周期证据的定稿/保留规则明确，不以辅助归档替代 SQLite 运行恢复所需证据。
- 只有文档变更。此前 pnpm check 的模块宿主 invalid_payload 失败已记录于会话，不能据此声称本次运行时代码已验证或新架构已实现。

## 结论

SQLite 权威订正消除了 DAG 当前 head、可重建全域索引及 Run 前根设计的主要复杂度。下一步应确认 R-03 的归档定稿/完成确认边界，再确认 R-04 的私有存储范围；不继续推进已被撤回的 DAG 事实源方案。
