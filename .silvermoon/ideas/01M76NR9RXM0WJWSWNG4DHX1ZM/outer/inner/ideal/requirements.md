# IPFS 模块加载需求

## 背景与目标

当前 [BundleCache](../../../../../../packages/task-engine/src/bundle.ts) 从调用者提供的 IPFS 客户端读取并验证 bundle，把 worker.cjs 保存为源码字符串；[引擎注册](../../../../../../packages/task-engine/src/bundle-engine.ts) 使用 ipfs://<cid>/worker.cjs 作为逻辑地址，但 [Worker 启动](../../../../../../packages/task-engine/src/type-supervisor.ts) 实际执行 new Worker(source, { eval: true })。不存在 bundle 源码临时落盘，也没有运行时 IPFS 模块解析 hook。

目标是让内容地址成为真正的模块加载地址，而非仅作为注册元数据。候选接入点为 Worker 内的模块 resolve/load hook；本需求规定可观察行为，不预先锁定某个 Node API 或 hook 线程模型。

## 地址与模块语义

- 支持以 ipfs://<cid>/worker.cjs 加载当前已验证 bundle 的入口；CID 和路径必须经统一解析、验证与规范化，禁止凭据、非法 CID、路径穿越及编码后越界。查询与片段不得被默默丢弃；首期不支持的形式应明确拒绝。
- 入口应具有可辨识的 IPFS 模块身份，加载失败包含足以定位模块的地址上下文，但不泄漏网关凭据或宿主敏感信息。
- 首期保持 Builder 的单文件 CJS 产物及其内置依赖打包方式，不承诺任意运行时相对模块图、ESM bundle、多文件资源执行或跨 CID 依赖。
- Node 内置模块保留既有使用行为；支持 IPFS 地址不代表开放宿主本地模块、node_modules 或任意外部协议。实现前核对现有能力，避免无意扩大或收紧既有权限。
- 对非入口 import、相对引用和 require 的首期支持范围必须在实施文档中明确；不能因为增加 hook 就隐式承诺所有 CJS/ESM 组合均可运行。

## 获取、校验与授权

- 复用已有内容客户端、DAG/CID 完整性校验、缓存、网关策略、并发与容量约束，不另建未经校验的源码下载路径，不依赖公共网关直连。
- 默认执行范围为当前已验证 bundle 的允许模块；CID 身份验证不等于代码执行授权。跨 CID 模块导入首期拒绝，不从资源读取权限推导模块执行权限。
- 共享内容块缓存不共享授权结论；不同 Run、Worker 和 bundle 不能借缓存命中绕过各自策略。相同 CID 在同一模块上下文中的身份应稳定。
- 与另一个 IPFS fetch idea 共享内容读取基础能力，但模块格式、模块执行授权、模块缓存语义属于本 idea；fetch 的 Response 语义不进入此处。

## 生命周期、兼容性与失败

- hook 必须在实际入口加载前安装，范围限于引擎管理的 Worker，不污染宿主或其他 Worker；不得把 hook 描述成安全沙箱。
- 保持任务输入、结果、消息、日志、取消、强制停止和资源释放语义。读取与加载受引擎/Run 生命周期约束；关闭后不得继续不受控拉取。
- 项目当前声明 Node >=22.13。实施前在最低版本及支持版本验证 hook、Worker 和 CJS 的兼容性，不假设新版本 API 已在最低版本可用。若无法在现有范围实现，应先提出兼容性决策，不能静默提高最低版本。
- 无效地址、未授权模块、缺失文件、不可达内容、校验失败、容量超限和取消均产生明确、可归因的失败，不回退为未校验执行、本地临时文件或隐式 eval。

## 验证场景与明确排除

成功场景覆盖实际 bundle 入口、内置模块及并发 Run；拒绝场景覆盖非法/编码路径、缺失或损坏内容、跨 CID、网关策略限制、容量限制及中途取消；兼容性场景覆盖现有任务生命周期和宿主加载行为。

本 idea 不改变 bundle 协议和 Builder 打包策略，不实现任意远程依赖安装，不提供 fetch API，不引入可变 IPNS 寻址，也不要求发布 npm 包。fetch idea 可独立推进，二者的共同约束是复用现有 IPFS 内容能力而非相互依赖功能完成。
