# 待决定项：类型化内容引用

本文件支持 [Idea](Idea.md)，只列尚未确定且影响构想收敛或实施可行性的决策。已确认设计见[讨论记录](Discussion.md)及[Content Payload 设计](../ContentPayload.md)。以下建议不是用户决定。

## B-01: 传输载荷与引用定位元数据

已确定 ContentPayload、ContentRef 命名，以及从类型和 discriminator 推导 JSONPath、数组尽可能使用通配符。尚需决定：

- 信封字段采用 data/contentRefPaths、data/cidPaths 或其他名称。
- 路径是否随每个载荷传输，还是由绑定契约提供；脱离 Task 的独立载荷如何保留引用语义。
- JSONPath 的受支持子集，以及嵌套判别条件不能安全合并时的具体位置回退方式。
- 收到路径元数据时以什么方式验证它与可信契约一致，不能任意把业务数据标成引用。

这是首要协议阻塞项，决定调用方、Worker、Result 消费方和独立工具包的边界。建议先明确载荷是否要求脱离原契约也能独立解码，再确定字段和元数据放置；不能同时把路径当成可省略的契约规则及独立载荷唯一的类型证据。

## B-02: 引用对象与受控内容能力

尚需明确 ContentRef 的作者侧与解码侧接口、创建已有 CID 引用的入口，以及对 raw、UnixFS 或一般 codec 节点的访问方式。是否复用 SpaceRef，不能仅由类型名字决定。

新内容写入须成功存储后才产生稳定引用，但写入 API 的输入编码、流式支持、取消和资源预算尚未定。工具包是否只做转换、由宿主工厂绑定只读能力，需要与传输契约一起明确；不得向 Worker 暴露完整 Store 或保留管理权限。

此项阻塞“移除可写 output Space 后 Worker 如何交付新内容”的可行性，不应推迟到实现中临时补接口。

## B-03: 内容保留责任与弱引用可用性

弱引用不自动授权、下载或保留内容，这一点已确定；具体可用性承诺尚未确定：

- Worker 新写入的内容从写入到 Result 发布期间由谁持有。
- 子任务结束、父任务继续或重组 Result 时，保留责任是否及如何交接。
- 发布失败、取消、崩溃及回收如何处理尚未交付的内容。
- 已有外部 CID 是否仅尽力读取，内容缺失或无权限如何向消费者报告。

此前“运行持有、发布时交接”只是候选，不是已批准策略。必须明确最低可用性承诺，才能证明成功返回的引用不会立即因子任务回收失效；不要求在本 Idea 中实现完整离线打包。

## B-04: 协议调整的覆盖范围

parameters/message/result 命名及保持现有 Schema/API V1 已确定。尚需明确：

- message 是否同样允许 ContentRef 并使用 ContentPayload；当前明确要求是 parameters/result。
- context.output、Run 的 output/cid/result 信封、Space、invokeTask、HTTP 和 CLI 的具体替代形状。
- 独立工具包是否暴露 TypeBox 构造器和宿主引用适配接口，以及构建与运行边界如何共享契约语义。
- 直接替换旧字段还是保留有限过渡入口；历史制品不因保持 V1 而被重写。

建议围绕一次启动、一次追加消息、一次子任务调用及一次最终结果消费画出统一边界，再确认替代范围。此项不重新争论已决定的字段命名或 Schema/API 版本。
