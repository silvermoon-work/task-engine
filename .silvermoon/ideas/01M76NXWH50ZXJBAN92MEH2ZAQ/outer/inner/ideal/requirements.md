# IPFS fetch 需求

## 目标与当前基础

为引擎管理的 Worker 提供 fetch("ipfs://<cid>/<path>")，让任务以熟悉的 Request/Response 方式读取内容，而非自行拼接公共网关 URL。复用 [IPFS 内容读取](../../../../../../packages/task-engine/src/content.ts)、[bundle 验证](../../../../../../packages/task-engine/src/bundle.ts) 和 [Run 资源边界](../../../../../../packages/task-engine/src/spaces.ts)，不引入独立的未验证下载通道。

与 [IPFS 模块加载 idea](../../../../01M76NR9RXM0WJWSWNG4DHX1ZM/outer/inner/ideal/Idea.md) 分别交付：本 idea 只读取数据，不使返回内容自动成为可执行模块；模块 hook 也不是 fetch 的必要前置。两者复用内容读取机制，但各自承担协议语义与授权判断。

## 调用入口与协议分流

- 引擎管理的 Worker 内支持 fetch 的字符串、URL 和 Request 输入，以及 RequestInit 中首期明确支持的选项。IPFS 地址进入内容适配层，HTTP(S) 保留既有 fetch 与网络策略，不改写为网关请求交给调用者。
- 不修改宿主全局 fetch 或 Undici dispatcher，不影响其他 Worker。适配必须在任务入口执行前可用。
- 不能假设配置 Undici dispatcher 就能让原生 fetch 接受 ipfs:。实施阶段验证实际运行时扩展点，优先使用局部、可测试的协议分流；具体安装方式不在构想阶段锁定。
- 首期支持 GET 与 HEAD，地址要求不可变 CID；不支持 IPNS、写入或上传。其他方法及不支持的选项要明确拒绝或按已声明的协议结果处理，不得静默忽略改变请求含义的参数。
- 统一规范化 CID 与路径，拒绝凭据、非法 CID、路径穿越和编码绕过；查询和片段的首期规则需显式声明，不得悄悄把不同请求归为同一地址。

## Response 与错误契约

- GET 返回标准 Response 形态，允许 text()、json()、arrayBuffer() 与 body 流消费；HEAD 返回相同资源的可用元信息但无正文，不为生成响应而完整读取正文。
- 响应地址应指向规范化 IPFS 地址，不暴露实际网关凭据；长度与类型元信息只能来自可信内容元数据或有依据的规则，不伪造 MIME 或完整性保证。无可靠依据时采用文档化的保守表示。
- 首期只支持文件内容，不把目录隐式转成网关 HTML 或可变目录索引。缺失文件与目录请求有确定、可测试的结果。
- 实施前明确缺失内容、方法不支持等协议结果的状态映射，以及地址错误、权限拒绝、传输失败、校验失败和超限的拒绝/流错误映射。遵循 fetch 对非成功状态与网络异常的区别，不把失败返回成 200 或空成功正文。
- 若损坏或传输错误在流消费中才发现，应使正文流失败；已返回 Response 不代表正文已全部验证。消费者只处理明确成功消费的数据，文档不得承诺不存在的全量预校验。
- 首期不承诺 Range、条件请求、HTTP 缓存验证器、自动重定向或网关专有头；其支持/拒绝行为必须写清，不让这些选项绕过容量或权限检查。

## 授权与内容基础能力

- 调用绑定当前活动 Run 的宿主能力，沿用资源读取授权边界；不允许仅靠伪造 Run ID、CID 或缓存命中借用其他任务权限。
- 能访问某个 CID 的内容不等于获准执行其中代码；fetch 权限与模块加载权限分别判断。首期不得因为增加 fetch 协议而默认开放任意 CID；额外授权能力应另行明确。
- 使用调用者提供的内容客户端与现有 DAG/CID 校验、网关 allow policy、缓存、并发与容量控制，不另建任意公共网关或绕过宿主策略的路径。
- 复用缓存时仍逐次判断授权；跨 Run 的缓存命中不得泄漏内容或复用授权结论。保持现有持久化与内容保留责任，不把读取变成隐式永久 pin。

## 流、取消与生命周期

- 正文按需流式读取并有背压和有界缓冲；不得为实现 Response 而无条件把完整资源复制进宿主和 Worker 内存。
- 请求 AbortSignal、body.cancel()、任务取消、Worker 退出和引擎关闭均应传递到实际内容读取；处理尚未开始、等待首字节与正文中途三种阶段。
- 若通过宿主与 Worker 通道传递正文，沿用在途数量及字节预算，消费者不读、消费慢或崩溃时仍可回收。
- 明确单请求、Run 与共享缓存的限制及释放责任；并发读取不能绕过总量上限。错误必须让调用者可观察，不以静默截断伪装成完整内容。
- 保持当前支持的 Node 范围。需要新增运行时能力时先验证兼容性并提出决策，不静默升级最低版本。

## 验证重点与非目标

成功场景覆盖文本、JSON、二进制、HEAD、分块及慢消费者；失败场景覆盖非法/编码路径、缺失文件、目录、未授权 CID、损坏内容、不可达网关、方法与选项限制、容量超限、各阶段取消。隔离验证覆盖宿主不变、HTTP(S) 不退化、并发 Run 不串权及退出无遗留读取。

本 idea 不实现模块执行 hook，不改变 bundle 格式，不实现 IPFS 写入、IPNS、任意跨 CID 授权或完整 HTTP 网关服务，也不要求发布 npm 包。
