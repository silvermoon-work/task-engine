# 任务依赖与 SpaceRef 子调用讨论

本文为 [Idea.md](./Idea.md) 的 supporting document，解释本轮讨论的方向、理由与边界，不另立契约，不表示已经实现或验收。实施与验证仍由[实施初版](../Implementation.md)逐步细化。

## 1. 讨论收敛

本轮讨论从“是否把 B 的节点直接纳入 A 的 Merkle node”出发，收敛为以下方向：

1. 静态依赖是父 bundle DAG 中对独立子 bundle 根的真实 CID 链接，分发与准备以整个静态依赖闭包为单位。
2. Context 启动子任务时必须使用 SpaceRef，不提供 CID 与 SpaceRef 的联合类型或平行调用入口；Engine 解析并固定执行 CID。
3. task-builder build 获取静态依赖并交付自包含 task folder；task-builder car 只从本地内容离线打包。
4. Builder 与 Engine 共用内容获取、验证和缓存实现，支持网关与本地 data dir 配置；默认读取独立公共内容配置，允许显式覆盖并使用不同实例。
5. task.build.yaml 用 imports: Record<Path, CID> 声明通用内容引入，不限于子任务；引入内容不可变，build 与 car 均校验其身份。
6. 不设置子任务启动授权关口；授权属于具体资源访问，本次不扩展通用 Node.js 文件、网络权限系统。

这里的“纳入”是建立 DAG 边，不是把 B 的节点字节塞进 A 的单个块，也不是把 B 的源码编译进 A 的 Worker。分发闭包与执行边界是两回事。

## 2. 为什么采用依赖 DAG

示意结构如下；B 和 C 的目标路径由 imports 声明，首版限制在 resources/ 下：

```text
A root
  task.yaml
  worker.cjs
  resources/tasks/
    B -> B root
    C -> C root
           resources/tasks/
             B -> 同一个 B root
```

### 内容复用与身份传播

- B 保持可独立验证、运行和复用的 bundle 根 CID。A 和 C 引用同一个 B 时，共享 B 的内容块，而不是制造两份不同身份的 B。
- 在同一个按 CID 存储的 blockstore 中，相同块可去重；父目录和依赖描述仍有自身开销。
- B 更新为新的根 CID 后，引用它的 A 的根 CID 随之变化。这是固定依赖版本、保证可复现性的预期行为。
- 内容复用要求实际块及其 CID 一致。逻辑相同的源码若生成了不同的 Worker 字节或采用不同的构建参数，不保证相同 CID。
- 独立分发的多个完整 CAR 仍可能各自携带 B 的块；内容寻址不会自动消除跨归档传输、校验、内存或 Worker 启动成本。共享存储复用不等于任意场景下零拷贝。

### 为什么不能只在声明里写 CID 字符串

普通文件中的 CID 文本不是 DAG 的可遍历边。若 B 只以字符串形式出现，递归遍历、导出或保留 A 的 DAG 不会因此自动包含 B。

因此静态依赖必须在内容图中真实可达。不要把 B 打成不透明归档文件放入 A 后，就把归档内的块当作已独立链接的 B；那会丢失所需的子根身份与直接 DAG 复用语义。

## 3. “一次准备完整”的准确承诺

需要区分三个状态：

| 状态 | 已保证的内容 | 尚未保证的内容 |
| --- | --- | --- |
| 创建 Space 视图 | 得到空间与路径的定位表达 | 块已下载、bundle 合法或可执行 |
| 解析 SpaceRef | 确定目标节点及其不可变 CID | 整个依赖闭包已准备完成 |
| 完整准备静态闭包 | 全部静态引入块已获取、验证并在承诺期间保留，执行目标通过 bundle 校验 | 永久 pin、外部长期可达或无限容量 |

要兑现完整准备，不能仅验证 A 的声明或拉取各 bundle 的目录元数据。必须递归获取并验证全部静态 import 内容，包括代码、Schema 和资源；普通文件或目录不因被引入就必须满足任务声明。只有执行目标需要通过任务 bundle 校验。缺块时不能返回成功形态的“已完整准备”。

准备与保留按唯一 CID 复用，同时对整个闭包设置明确容量边界，避免共享依赖重复获取，也避免巨大闭包无界占用资源。块去重不意味着免除路径、依赖展开和执行次数等逻辑预算。

运行依赖的保留必须覆盖所承诺的运行期间，不能因为准备操作结束就释放唯一可用内容。关闭内容来源后仍能执行已完整准备的静态闭包，是验证该承诺的直接方式。Engine 内部租约或缓存不应被描述成对共享 IPFS 节点的永久 pin。

首版完整准备不提供“成功但内容未齐”的懒加载分支；超限明确失败，不自动降级。动态 SpaceRef 在调用时完整准备目标闭包，并使用同一套容量规则，但不承诺在准备 A 时已经获取。

存储容量按唯一块计算，文件数、路径展开和调用次数独立限额。首版不实现自动内容 GC，运行期间不回收所需内容；停止使用的租约和内存资源仍须正常释放。以后增加回收时再定义跨进程保留协调，不把永久磁盘保留承诺无限延伸。既有按需读取行为需要显式迁移，不能冒充完整准备。

## 4. 子任务调用只接受 SpaceRef

以下是目标 API 的说明性示例，尚不是已实现接口；字段名称及最终类型声明由实施阶段确定：

```ts
// 父 bundle 内的静态依赖。
await context.invokeTask({
  key: "step-b",
  bundle: context.bundle.root.resolve("resources/tasks/B"),
  input: { value: 42 },
  timeoutMs: 5000,
});

// 已知外部 CID：先创建静态 Space 视图，再走同一调用入口。
await context.invokeTask({
  key: "external-b",
  bundle: context.space(cid).root,
  input: { value: 42 },
  timeoutMs: 5000,
});
```

不增加第二个按 CID 启动子任务的方法，也不要求作者同时填写目标 CID 和路径。沿用 context.space(cid) 即可，不必为了这个能力引入 openSpace 别名。

这一统一只针对 Context 的子任务启动接口，不意味着外部提交请求也必须改成 SpaceRef，不改变业务 input 的含义。

### SpaceRef 与 CID 的分工

- SpaceRef 回答“哪个空间中的哪个节点”；CID 回答“确切执行哪份不可变内容”。
- SDK 接收当前 Context 创建的真实 SpaceRef，并转换成跨 Worker 的协议引用，不直接传输包含方法的 JavaScript 对象。
- 协议引用中的 sid 和 path 是定位信息，不是访问凭证；不能因为调用方能构造同形 JSON 就信任来源或给予权限。
- Engine 解析目标目录，取得实际根 CID，校验其为合法任务 bundle，再以该 CID 准备、记录和执行。
- 作者无需把 B 的 CID 硬编码进 A 的 Worker；构建产物中的真实 DAG 链接承担依赖固定。

## 5. 不同来源使用同一个接口，但承诺不同

| SpaceRef 来源 | 依赖性质 | 调用边界 |
| --- | --- | --- |
| A 自身 bundle 中的子目录 | 静态依赖 | 目标必须是合法子 bundle；纳入声明的静态依赖闭包准备 |
| 外部 context.space(cid) 中的根或子目录 | 动态依赖 | 调用时准备，不额外设置子任务启动授权，不自动享有 A 的完整准备承诺 |
| 当前 Run 的可写 output | 可变来源 | 首版明确拒绝，不暗中按当前内容执行 |

支持外部 SpaceRef 是对当前父 DAG 子树调用范围的显式扩展。内外部引用的区别是准备时机和内容来源，不是子任务启动权限。内容获取仍遵守已有的资源访问策略与网关配置，动态引用不能绕过这些约束。

未来若支持可写 output，必须先定义调用时的不可变快照、并发写入顺序和重试身份。子任务不得跟随父 output 后续变化；本 idea 首版不承担这项扩展。

## 6. Engine 解析、资源边界与幂等

职责顺序在语义上包括：

1. 验证引用形式、静态来源与父 Run 的有效性；实际内容访问沿用资源层的访问约束。
2. 在容量与取消边界内解析目标目录，取得实际执行 CID，验证目标 bundle，不调用额外的子任务授权策略。
3. 把来源引用与解析后的执行 CID 绑定到这次调用，持久化必要身份，然后完整准备和启动独立子任务。

这一描述不预先规定内部事务或缓存实现，但要求失败、重试和恢复均满足以下不变量：

- 同一父 Run 内的 key 表示同一次调用意图。修改引用、input 或其他受幂等保护的字段，不能偷偷复用旧调用。
- 一旦调用身份固定，重复请求或丢失响应后的重试沿用该 CID，不通过重新解释路径切换目标。
- 恢复时不能只保留一个来源路径、丢失已固定的 CID，也不能把内容暂时不可用解释为允许替换实现。
- 目录不存在、目标不是目录、bundle 非法、资源访问被拒绝、内容缺失或超限，都必须明确失败。

### 固定身份的持久化与恢复

以 parentRunId + key 标识一次调用。记录规范化来源引用、input、超时意图、解析后固定的目标 CID、稳定的子提交 requestId、确定的 deadline 和处理状态。

派发前必须持久化执行目标与子提交身份。同 key 同意图复用原调用；不同意图明确冲突。响应丢失或进程恢复后，查询或继续同一个子提交，不新建另一份身份。已固定的内容缺失时只获取同一个 CID，或明确失败，不替换目标。具体原子写入顺序和崩溃窗口由实施测试验证；这保证身份不重复、不漂移，不承诺业务外部副作用天然 exactly-once。

### 不在子调用上设置授权关口

此前提出的 authorizeChild 扩展、按目标 CID 允许或拒绝子调用，以及子调用前询问用户的建议，已被本轮讨论明确替代。实现应移除现有子任务启动授权要求，任务不需要在 run 中自报授权信息，宿主也不必配置子调用白名单或逐次确认。

权限关口属于具体资源及操作：任务访问受控资源时，由相应宿主资源机制决定允许、拒绝或是否询问用户。切换子任务或目标 CID 不能扩大已有资源权限；缓存命中与 DAG 可达也不授予额外资源权限。身份校验、引用有效性、任务准入和调度预算仍然存在，但不是新增的子调用授权。

本次保留已有资源访问约束，不建设通用资源权限框架，不声称 Worker 是 OS 安全沙箱。只有经过受控资源入口的访问才受该入口约束，不能声称覆盖任意 Node.js 文件或网络访问。

## 7. 保留任务执行边界

B 纳入 A 的分发 DAG，不代表 B 变成 A 的普通函数调用。B 仍保持独立任务与 Run 身份、输入和结果校验、资源访问约束、超时、取消及子调用预算；A 的依赖完整性不能代替这些执行检查。

静态依赖图必须可构造为 Merkle DAG，不能用循环 CID 链接表达相互递归。运行时递归调用是另一种执行行为，即使未来支持，也仍需深度、总量与并发限制，不能由静态图复用推导出无限调用能力。

把 SpaceRef 作为“要执行的 bundle”与把 SpaceRef 作为“子任务的数据输入”也是两件事。本轮只收敛前者；不附带引入跨 Run 可写空间共享或任意引用反序列化能力。

## 8. 现有基础与待确定细节

讨论时的代码已具备以下基础，但这些事实不等于新方案已经实现：

- [组合测试](../../../../../../packages/task-engine/test/composition.test.ts)将子 bundle 文件树放在父 bundle 的 resources/child，并覆盖父、子、孙调用。
- [现有调用类型](../../../../../../packages/task-protocol/src/run.ts)要求 cid 与 path；[Engine 调用逻辑](../../../../../../packages/task-engine/src/bundle-engine.ts)核对子树根 CID，现有 authorizeChild 默认拒绝。这是要改变的现状，不是目标权限模型。
- [SpaceRef 类型](../../../../../../packages/task-protocol/src/spaces.ts)已有空间与路径表达；[SDK Space 实现](../../../../../../packages/task-sdk/src/spaces.ts)已有引用创建与协议转换机制可供复用。
- [现有准备语义](../../../../../../packages/task-engine/README.md)允许 binary 后继块按需读取，因此还不能直接宣称完整离线闭包保证。

原先四项待定问题已收敛到以下语义，剩余底层实现仍须验证：

| 问题 | 已确认方向 | 实施阶段验证 |
| --- | --- | --- |
| 声明和任务边界 | task.build.yaml 的 imports: Record<Path, CID> 引入通用文件或目录，首版目标在 resources/ 下；执行时才校验任务目标 | 与精确 include、binary 和当前规范化读取的衔接 |
| 原始 CID 保真 | build 获取并保留原始 DAG，car 离线校验路径对应 CID；import 不可变，修改后失败 | 自包含任务目录的块和元数据布局，以及展开内容的一致性 |
| 完整准备与保留 | 全静态闭包准备、唯一块计存储、独立逻辑预算、超限失败，首版不自动 GC | 具体容量默认值、边界测试和旧按需读取行为迁移 |
| 权限与恢复 | 移除子调用授权，保留资源访问约束；派发前固定目标和子提交身份 | 现有资源约束不退化，持久化原子性及故障恢复 |

未完成的是验证与数据布局，而不是继续悬置已明确的产品语义。独立公共配置的路径、键名及既有配置迁移仍需在实施时确定。

## 9. build 收集依赖，car 离线交付

后续讨论进一步明确职责边界：

```text
源码与静态依赖声明
  -> build：解析、获取、验证并形成完整 task folder
  -> car：读取本地内容，遍历去重并编码完整 CAR
  -> Engine：导入或获取、固定执行身份、完整准备与运行期间保留
```

### build 的成功条件

- 先使用本地已验证内容或已有 CAR，再通过显式配置的来源补齐缺块；“拉资源”不意味着每次必须联网。
- 任务目录必须自包含完整静态依赖闭包，不能把尚未兑现的远端 CID 占位符当作构建成功的完整产物。动态依赖不在此承诺内。
- 放入目录的 B 是已构建制品，不是需要重新编译的作者源码。不得改写其文本、重新规范化资源或以其他方式改变 B 的执行身份。
- 若采用展开文件树形式，必须验证该子树重新形成的根 CID 与依赖声明一致；无法保真就明确失败，不能悄悄把 B 换成另一个 CID。
- 文件目录如何保留 UnixFS 元数据、原始 DAG 分块和子根身份，需要实施验证；“有同名文件”不能代替 CID 相等。若须保存辅助块或元数据，它们必须随完整 task folder 一起交付，不能隐式依赖机器缓存才能离线打包。

### 通用 imports 声明与不可变规则

task.build.yaml 使用 imports: Record<Path, CID>，例如：

```yaml
imports:
  resources/tasks/resize: "<bundle-directory-cid>"
  resources/models/model.bin: "<file-cid>"
  resources/templates: "<directory-cid>"
```

key 是产物 task folder 内的目标路径，value 是固定的精确 CID，不是版本范围或可变名称。目标支持文件或目录，不限于任务 bundle。首版目标限定 resources/，不顺带开放任意根级路径。

普通文件中的 CID 声明是 build 输入；build 必须把它转换成真实 DAG 链接并获取其可达内容。引入、include 和生成文件之间出现路径冲突或文件/目录覆盖时明确失败，不隐式合并或覆盖。引入内容不套用本地作者文件的改写流程，避免改变内容身份。

import 视为不可变制品。用户修改引入内容后，car 校验必须失败；要修改内容，应从 imports 移除对应项，转为本地资源，再按本地资源规则构建为新的 CID。

### car 的成功条件

car 不补下载，不选择远端，也不因读取到网关配置就联网。底层编码器从本地可读 DAG 获取块，完成验证、遍历、去重与编码；缺块明确失败。

build 获取时校验 CID；car 再核对各 import 路径的实际根 CID 与随产物保留的预期 CID。task folder 必须保留路径到 CID 的绑定及还原原 DAG 所需的内容，不能要求 car 回查原作者工程或机器缓存。仅校验不能恢复丢失的 UnixFS 元数据或分块，因此要复用原始 import DAG，不把重新编码后不一致的结果当作原制品。

如果 task folder 同时保留展开文件和原始块，car 还必须验证两者一致性；不能仅验证未变的块备份而忽略用户修改过的展开内容。最终具体存储形式由实施验证决定。

完整 CAR 必须包含从 A 根可达的全部静态依赖块，而不是只写入指向 B 的链接。同一 CAR 中共享块按 CID 去重。生成完整 CAR 不代表 Engine 已导入或取得运行期间保留能力；交付准备不能代替执行准备。

task-builder build 若沿用现有默认同时生成 CAR 的工作流，也必须先完成上述构建职责，再调用同一个离线编码步骤；不需要仅为分层而强行增加用户操作。

## 10. 共用内容机制，不耦合任务生命周期

Builder 与 Engine 应依赖共同的内容能力，而不是让 Builder 依赖 Engine，或直接复用 Engine 的整个 BundleCache：

```text
Builder build ----+
                 +-> 内容获取、CID 验证、DAG 读取、块缓存
Engine ----------+

car -> 同一内容机制的本地读取能力，不启用远端获取
```

共享范围包括本地命中、从配置来源获取缺块、CID 校验、在途请求去重、DAG 遍历、超时、取消、容量限制和明确错误。具体实现复用现有 IPFS/UnixFS 组件，不重新实现协议。

上层仍分别负责：

| 调用方 | 独有职责 |
| --- | --- |
| Builder | 作者依赖解析、构建完整性、task folder 交付 |
| CAR 编码 | 本地 DAG 的完整验证与编码，不下载 |
| Engine | SpaceRef 解析、身份固定、准入、任务调度和运行租约，实际内容访问遵守资源层约束 |

库层接受可注入的内容端口；命令行或宿主负责加载配置和拥有客户端生命周期。不要让通用库在导入时隐式读取用户配置、启动节点或关闭其他调用方的共享实例。

### 公共默认配置

用户已选择独立公共内容配置，而不是让 Builder 读取 Engine 专属 server.* 配置：

- Builder 和 Engine 均支持 IPFS gateway 与本地 data dir 配置。
- 未覆盖时，两者读取同一个公共默认来源，从而默认使用同一份本地内容存储。
- 允许各自显式覆盖，使用不同网关、不同目录或不同客户端实例；共享实现不是强制单例。
- 公共内容配置只管内容服务与存储，不包含任务历史、日志或 Engine 运行数据库。公共配置的最终文件路径、键名及既有配置迁移方式尚未确定。
- 配置了网关不代表授权任意资源访问；不引入未配置的公共网关回退，也不绕过已有资源约束。这里不新增子任务启动政策。

“默认同一个实例”在不同部署方式下须精确解释：同一进程可以注入同一个客户端；不同进程不能共享 JavaScript 对象，但可以访问同一内容目录或同一内容服务。此方向不要求一个强制常驻服务，也不排除以后由宿主选择服务化部署。

### 同目录并发与保留

共享目录不是简单地把两个私有缓存路径设成相同字符串。实现必须证明：

- 并发写入只发布完整且通过 CID 校验的块；中断或失败不留下可被误读为成功的缓存项。
- 一个调用方的关闭或清理不破坏另一个调用方正在使用的内容。首版不自动删除已存内容块；以后加入回收时必须协调运行期保留。
- 多进程共享存储不等于已自动实现跨进程下载去重；是否协调在途下载及其机制，需要单独验证。
- 缓存命中只证明本地有相应内容，不授予受限资源访问权限；子任务执行本身不另设授权。

缓存后端、跨进程写入协调和容量实现属于实施阶段的技术选择，自动回收明确留到后续。应优先采用能满足已有不变量的最简单机制，不为“共享”额外引入全局服务或未经验证的锁定方案。
