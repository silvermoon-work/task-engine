# 讨论起点：结构化输出与 Blob

## 来源与当前决定

2026-11-13，用户在 OKR Agent 项目讨论 Check 与 Objective Probe 的关系时提出本想法，并要求转入 Task Engine 新建 Idea，留待后续思考和讨论。当前只授权记录想法，不表示方案完善、已通过构想验收或可以开始实施。

用户的核心提议是：将 Task 最终输出的 result 和 output 结合，不再要求输出表达文件系统，而是表达扩展 JSON object，新增 Blob 元素；整体可以编码为 Merkle DAG，使 problems 及其 reference 文档更容易组织。

## 触发问题

- Check 已将问题参考文档直接交付在 output space 中，消费方不应二次查询原始 Check 包。
- 多个问题可能引用同一份参考文档；参考文档还可能引用其他文档、图片或示例。
- 父 Check 可以调用其他 Check；仅交付父包自己的 references 不足以覆盖跨包及嵌套引用。
- 将子 output 挂载为目录是一种方案，但文件树不一定适合作为所有 Task 输出的基础模型。

## 候选方向，均未定案

- 逻辑输出是包含 JSON 基础类型、数组、对象及 Blob 的结构化值；作者表达业务结构，底层处理编码、分块与内容寻址。
- 业务结果与附属内容拥有统一的输出根身份，而不是必须分成 JSON 结果和可写文件目录。
- 父任务可以组合子输出中的值或引用，不必读取全部 Blob 到内存，也不必手工复制、扁平化或改写目录。
- 共享内容由 Merkle DAG 复用；CAR 是承载块的传输容器，不要求根表示文件树，也不要求中间节点有文件名。
- 文件树可作为一种业务数据模型或导出视图，不必成为通用输出模型。

## 后续需要讨论

1. **值与引用类型**：只增加 Blob 是否足够？是否需要通用结构化子值引用？作者 API、序列化形式、Schema 校验及普通 JSON 的边界是什么？
2. **文档依赖**：Markdown 的链接只是正文中的字节，不会自动变成 IPLD Link。正文、共享标准及附属资源如何关联、解析并校验？这些语义属于 Check/文档层还是通用资源层？
3. **循环引用**：文档语义可能互相引用，不能直接构造循环的 Merkle 链接。是否通过逻辑 ID、资源表或其他间接机制表达？
4. **父子组合与生命周期**：父任务如何取得子输出并保留部分或全部内容？子运行结束、临时资源回收或父任务取消时如何保证已交付内容有效？
5. **交付完整性**：CAR 不自动保证引用闭包完整。最终制品如何包含或保证可获取所需块？缺块、外部 URL、访问授权与资源限制如何处理？
6. **磁盘物化**：一般 DAG 可以通过块文件和清单等映射无损落盘，但没有天然唯一的业务文件树。是否提供无损导出、可浏览文档导出，或两者都提供？路径分配及链接转换如何定义？
7. **兼容与消费体验**：现有 result、output.cid、Space、invokeTask、CLI 展示和消费者如何兼容或迁移？按需读取 Blob 的接口如何设计？
8. **存储策略**：根编码、节点边界、Blob 分块、元数据与确定性如何约定？内容去重不意味着能忽略语义不同的引用上下文。

## 候选验证场景

子 Check 返回两个问题，二者共享一份标准，标准另引示例资源；父 Check 组合该结果，并可能组合更深层子检查。消费者仅获得最终约定交付物，就能读取问题及完整参考资源，不查询原始 Check 包。对资源缺失和未声明依赖应能明确失败。

该场景用于后续比较方案，不是已批准的 API 或实施任务。是否移除 Objective Probe 是另一个架构议题，不在本 Idea 中顺带决定。
