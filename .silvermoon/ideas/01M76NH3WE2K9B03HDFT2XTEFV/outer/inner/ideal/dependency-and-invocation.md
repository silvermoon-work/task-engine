# 任务依赖与 SpaceRef 子调用讨论

本文为 [Idea.md](./Idea.md) 的 supporting document，解释本轮讨论的方向、理由与边界，不另立契约，不表示已经实现或验收。实施与验证仍由[实施初版](../Implementation.md)逐步细化。

## 1. 讨论收敛

本轮讨论从“是否把 B 的节点直接纳入 A 的 Merkle node”出发，收敛为两个相互配合的方向：

1. 静态依赖是父 bundle DAG 中对独立子 bundle 根的真实 CID 链接，分发与准备以整个静态依赖闭包为单位。
2. Context 启动子任务时必须使用 SpaceRef，不提供 CID 与 SpaceRef 的联合类型或平行调用入口；Engine 解析并固定执行 CID。

这里的“纳入”是建立 DAG 边，不是把 B 的节点字节塞进 A 的单个块，也不是把 B 的源码编译进 A 的 Worker。分发闭包与执行边界是两回事。

## 2. 为什么采用依赖 DAG

示意结构如下；目录名称只是说明，不预先规定最终 bundle 布局：

```text
A root
  task.yaml
  worker.cjs
  dependencies/
    B -> B root
    C -> C root
           dependencies/
             B -> 同一个 B root
```

### 内容复用与身份传播

- B 保持可独立验证、运行和复用的 bundle 根 CID。A 和 C 引用同一个 B 时，共享 B 的内容块，而不是制造两份不同身份的 B。
- 在同一个按 CID 存储的 blockstore 中，相同块可去重；父目录和依赖描述仍有自身开销。
- B 更新为新的根 CID 后，引用它的 A 的根 CID 随之变化。这是固定依赖版本、保证可复现性的预期行为。
- 内容复用要求实际块及其 CID 一致。逻辑相同的源码若生成了不同的 Worker 字节或采用不同的构建参数，不保证相同 CID。
- 独立分发的多个完整 CAR 仍可能各自携带 B 的块；内容寻址不会自动消除跨归档传输、校验、内存或 Worker 启动成本。共享存储复用不等于任意场景下零拷贝。

### 为什么不能只在声明里写 CID 字符串

普通文件中的 CID 文本不是 DAG 的可遍历边。若 B 只以字符串形式出现，递归遍历、导出或保留 A 的 DAG 不会因此自动包含 B。

因此静态依赖必须在内容图中真实可达。不要把 B 打成不透明归档文件放入 A 后，就把归档内的块当作已独立链接的 B；那会丢失所需的子根身份与直接 DAG 复用语义。

## 3. “一次准备完整”的准确承诺

需要区分三个状态：

| 状态 | 已保证的内容 | 尚未保证的内容 |
| --- | --- | --- |
| 创建 Space 视图 | 得到空间与路径的定位表达 | 块已下载、bundle 合法或可执行 |
| 解析 SpaceRef | 确定目标节点及其不可变 CID | 整个依赖闭包已准备完成 |
| 完整准备静态闭包 | 所需块和各子 bundle 已获取、验证并在承诺期间保留 | 永久 pin、外部长期可达或无限容量 |

要兑现完整准备，不能仅验证 A 的声明或拉取各 bundle 的目录元数据。必须递归获取并验证静态依赖，以及执行所需的代码、Schema 和资源内容；缺块时不能返回成功形态的“已完整准备”。

准备与保留按唯一 CID 复用，同时对整个闭包设置明确容量边界，避免共享依赖重复获取，也避免巨大闭包无界占用资源。块去重不意味着免除路径、依赖展开和执行次数等逻辑预算。

运行依赖的保留必须覆盖所承诺的运行期间，不能因为准备操作结束就释放唯一可用内容。关闭内容来源后仍能执行已完整准备的静态闭包，是验证该承诺的直接方式。Engine 内部租约或缓存不应被描述成对共享 IPFS 节点的永久 pin。

若保留按需加载模式，必须与“完整准备”明确区分；不能把父 bundle 已受理直接等同于可离线执行。具体配置和生命周期接口在实施阶段确定。

## 4. 子任务调用只接受 SpaceRef

以下是目标 API 的说明性示例，尚不是已实现接口；字段名称及最终类型声明由实施阶段确定：

```ts
// 父 bundle 内的静态依赖。
await context.invokeTask({
  key: "step-b",
  bundle: context.bundle.root.resolve("dependencies/B"),
  input: { value: 42 },
  timeoutMs: 5000,
});

// 已知外部 CID：先创建静态 Space 视图，再走同一调用入口。
await context.invokeTask({
  key: "external-b",
  bundle: context.space(cid).root,
  input: { value: 42 },
  timeoutMs: 5000,
});
```

不增加第二个按 CID 启动子任务的方法，也不要求作者同时填写目标 CID 和路径。沿用 context.space(cid) 即可，不必为了这个能力引入 openSpace 别名。

这一统一只针对 Context 的子任务启动接口，不意味着外部提交请求也必须改成 SpaceRef，不改变业务 input 的含义。

### SpaceRef 与 CID 的分工

- SpaceRef 回答“哪个空间中的哪个节点”；CID 回答“确切执行哪份不可变内容”。
- SDK 接收当前 Context 创建的真实 SpaceRef，并转换成跨 Worker 的协议引用，不直接传输包含方法的 JavaScript 对象。
- 协议引用中的 sid 和 path 是定位信息，不是访问凭证；不能因为调用方能构造同形 JSON 就信任来源或给予权限。
- Engine 解析目标目录，取得实际根 CID，校验其为合法任务 bundle，再以该 CID 准备、记录和执行。
- 作者无需把 B 的 CID 硬编码进 A 的 Worker；构建产物中的真实 DAG 链接承担依赖固定。

## 5. 不同来源使用同一个接口，但承诺不同

| SpaceRef 来源 | 依赖性质 | 调用边界 |
| --- | --- | --- |
| A 自身 bundle 中的子目录 | 静态依赖 | 目标必须是合法子 bundle；纳入声明的静态依赖闭包准备 |
| 外部 context.space(cid) 中的根或子目录 | 动态依赖 | 由宿主单独授权与准备，不自动享有 A 的完整准备承诺 |
| 当前 Run 的可写 output | 可变来源 | 首版明确拒绝，不暗中按当前内容执行 |

支持外部 SpaceRef 是对当前父 DAG 子树调用范围的显式扩展，不是因为统一类型就自动放开任意来源。宿主可以允许父 DAG 内的子任务，同时拒绝外部任务。

未来若支持可写 output，必须先定义调用时的不可变快照、并发写入顺序和重试身份。子任务不得跟随父 output 后续变化；本 idea 首版不承担这项扩展。

## 6. Engine 解析、授权与幂等

职责顺序在语义上包括：

1. 验证引用形式、来源与父 Run 的有效性，先应用可判定的来源访问策略。
2. 在容量与取消边界内解析目标目录；如授权依赖目标 CID，取得 CID 后再执行目标级调用授权，不能先下载完整闭包再判断是否允许。
3. 把来源引用与解析后的执行 CID 绑定到这次调用，持久化必要身份，然后准备和启动独立子任务。

这一描述不预先规定内部事务或缓存实现，但要求失败、重试和恢复均满足以下不变量：

- 同一父 Run 内的 key 表示同一次调用意图。修改引用、input 或其他受幂等保护的字段，不能偷偷复用旧调用。
- 一旦调用身份固定，重复请求或丢失响应后的重试沿用该 CID，不通过重新解释路径切换目标。
- 恢复时不能只保留一个来源路径、丢失已固定的 CID，也不能把内容暂时不可用解释为允许替换实现。
- 目录不存在、目标不是目录、bundle 非法、未授权、内容缺失或超限，都必须明确失败。

解析前的来源检查和解析后的 CID 授权是两个层次；SpaceRef 可达、已缓存或已纳入父 DAG，都不能绕过宿主调用政策。

## 7. 保留任务执行边界

B 纳入 A 的分发 DAG，不代表 B 变成 A 的普通函数调用。B 仍保持独立任务与 Run 身份、输入和结果校验、授权、超时、取消及子调用预算；A 的依赖完整性不能代替这些执行检查。

静态依赖图必须可构造为 Merkle DAG，不能用循环 CID 链接表达相互递归。运行时递归调用是另一种执行行为，即使未来支持，也仍需深度、总量与并发限制，不能由静态图复用推导出无限调用能力。

把 SpaceRef 作为“要执行的 bundle”与把 SpaceRef 作为“子任务的数据输入”也是两件事。本轮只收敛前者；不附带引入跨 Run 可写空间共享或任意引用反序列化能力。

## 8. 现有基础与待确定细节

讨论时的代码已具备以下基础，但这些事实不等于新方案已经实现：

- [组合测试](../../../../../../packages/task-engine/test/composition.test.ts)将子 bundle 文件树放在父 bundle 的 resources/child，并覆盖父、子、孙调用。
- [现有调用类型](../../../../../../packages/task-protocol/src/run.ts)要求 cid 与 path；[Engine 调用逻辑](../../../../../../packages/task-engine/src/bundle-engine.ts)核对子树根 CID，默认需要宿主显式授权。
- [SpaceRef 类型](../../../../../../packages/task-protocol/src/spaces.ts)已有空间与路径表达；[SDK Space 实现](../../../../../../packages/task-sdk/src/spaces.ts)已有引用创建与协议转换机制可供复用。
- [现有准备语义](../../../../../../packages/task-engine/README.md)允许 binary 后继块按需读取，因此还不能直接宣称完整离线闭包保证。

以下细节留待实施阶段根据现有协议与验证结果确定，不当作已讨论通过的具体方案：

- 静态依赖的声明格式与目录布局，以及如何在精确 include 清单下识别任务边界。
- 构建器如何直接接入并保持已有子 bundle 的 DAG 和根 CID，而不是要求作者手工重复铺设文件树。
- 闭包预算、运行期间保留机制，以及完整准备与既有按需读取模式的接口关系。
- 来源授权与目标 CID 授权的具体宿主接口，以及固定身份的持久化和恢复协议。

这些待定细节不能改变本轮方向：子调用入口只有 SpaceRef，执行身份由 Engine 固定，静态依赖通过真实 DAG 链接形成有界、可完整准备的闭包。
