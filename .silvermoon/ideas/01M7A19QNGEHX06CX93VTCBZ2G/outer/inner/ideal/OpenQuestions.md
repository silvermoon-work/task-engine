# 待决定项：类型化内容引用

本文件支持 [Idea](Idea.md)，只列尚未确定且影响构想收敛或实施可行性的决策。已确认设计见[讨论记录](Discussion.md)及[IPFS Payload 设计](../IpfsPayload.md)。以下建议不是用户决定。

## B-01: 传输载荷与引用定位元数据

已确定 IpfsPayload、ContentRef 命名，以及从类型和 discriminator 推导 JSONPath、数组尽可能使用通配符。2026-11-14 用户进一步确认方案 A：每个载荷自带路径，可脱离原 Task 契约识别引用；仅依赖绑定契约的方案 B 不作为默认协议。尚需决定：

- JSONPath 的受支持子集，以及嵌套判别条件不能安全合并时的具体位置回退方式。
- 收到路径元数据时以什么方式验证它与可信契约一致，不能任意把业务数据标成引用。

载荷独立性与元数据放置的主要取舍已解决；2026-11-14 用户将引用路径字段定名为 cidPaths。受支持的定位与验证规则需在实现前收敛，不重新争论方案 A/B 或已确定的引用字段名。

## B-02: 引用对象与受控内容能力

2026-11-14 用户确认引用访问方案 A：ContentRef 只表示不可变 CID 身份，读取通过 context 提供的受控内容能力进行，不把读取方法或访问权限绑定到引用上。工具包与宿主 I/O 分离的主要取舍已解决。

用户进一步收敛 context 内容能力为按 CID 读取、CID 加 path 解析目标 CID、临时存入内容并返回 CID。文件读取采用流；尚需明确目录通过读取节点携带条目流，还是通过独立枚举操作提供条目，不能以只读封装拆包代替底层目录能力。还需明确工具包如何在作者侧构造或识别真实 ContentRef/CID 类型，以及 raw、UnixFS 或一般 codec 节点的读写与路径语义。写入须成功存储后才返回 CID，但输入编码、流式写入、取消和资源预算尚未定。不得向 Worker 暴露完整 Store 或保留管理权限。

IpfsAccess 归属 ipfs-access，宿主提供实现，ipfs-tree 提供按需引入的只读便利封装，SDK 和 ipfs-payload 不依赖或重新导出 ipfs-tree。接口归属和依赖边界已确定；内容模型及节点返回形状仍需在实现前明确，不临时猜测 codec。

## B-03: 内容保留责任与弱引用可用性

2026-11-14 用户确认“本地新内容由运行临时持有，结果发布后由结果持有”的原则；运行结束不解除结果持有，清理跟随结果策略。父子可同时持有同一内容，交接先取得新持有再释放旧持有，必要保留责任未建立不能成功发布。取消或崩溃后的临时持有须可恢复地清理。

外部缺失 CID 不自动下载或获得持久可用性承诺，缺失及无权限明确失败；保留资源的强 DAG 子块不等于遍历文档弱引用。主要生命周期取舍已解决。

结果清理接口、持有关系的持久化与恢复、已有本地内容再次引用的处理仍需在实施中细化，不预设固定保留天数，不要求本 Idea 实现完整离线打包。

## B-04: 协议调整的覆盖范围

2026-11-14 用户确认全部切换：三个通道、父子调用和外部 SDK/HTTP/CLI 使用统一 IpfsPayload，不维护旧 input/output 交换协议。Task/Worker 对外 Space 接口由三种 CID 内容能力替代，Bundle 与子任务目标改以 CID 表达；内部 Builder 文件树及存储实现不因此全面删除。保持已有 Schema/API V1，历史制品不重写或承诺兼容。

主要覆盖范围已解决。具体 Run/result 控制信封、Bundle CID 字段、TypeBox 构造器及作者侧引用类型由主体世界继续细化；不把这些方法命名问题重新当成全量替换的授权阻塞。
