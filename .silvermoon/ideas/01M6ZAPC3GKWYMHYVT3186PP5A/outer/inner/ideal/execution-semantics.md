# CLI 单次执行：语义与边界

本文支撑 [构想契约](Idea.md)，描述需要接受的使用行为、实际能力和风险，
不是另一份契约或已经完成的实现设计。以下命令和接口名均为示意。

## 使用体验

```powershell
task-engine run <bundle-cid> --input .\input.json
```

命令指定一个 Bundle 及输入，启动嵌入式 engine，提交根 Request，
持续执行本次工作的闭包，待全部有限工作结束并完成清理后返回 shell。
调用者不需要先启动 task-engine HTTP service。
独立内容源仍需可用；“无需 task-engine 服务”不等于“不依赖 Gateway 或其他业务资源”。

现有生产准入以 Bundle 根 CID 或 `{cid, hint}` 为身份，不以任务名称选择当前版本。
CID/Gateway 路径沿用此契约；本地 CAR 路径先完整校验并读取唯一 Bundle 根 CID，
再将其提交给同一个 engine，内容由 CAR 的只读块源提供，不需要另起 Gateway。
支持可选 expected CID 检查；不将 CAR 路径或文件摘要当作 Bundle 身份。
本地源码构建、目录执行、上传或持久 IPFS 导入不在本次范围内。

```powershell
task-engine run --car .\bundle.car --input .\input.json
```

本地 CAR 与 CID/Gateway 是互斥内容源。CAR 校验与执行保持有界读取、取消、
整次预算和最终释放；损坏、缺块、多余块、错误 Schema 或 expected CID 不匹配
不能启动 Worker，也不能 fallback 到网络。CAR 包含的子树沿用已有派生权限与预算。

## 现有代码事实

依据当前基线 `a450399ea3a7`，区分已存在能力与本次待做能力：

| 表面 | 已存在能力 | 本次缺口或限制 |
| --- | --- | --- |
| [engine 公共入口](../../../../../../packages/task-engine/src/index.ts) | 可程序化创建嵌入式 engine | 没有直接执行指定 Bundle 的 CLI |
| [Bundle engine](../../../../../../packages/task-engine/src/bundle-engine.ts) | `start`、`submit`、异步 preparation、Task/Run 观察、`close` | 没有公开的全体工作耗尽等待接口 |
| [Coordinator](../../../../../../packages/task-engine/src/engine.ts) | 持续 tick、运行协调及退出/回收管理 | 持续调度本身不会因业务工作结束而自动停止 |
| [子任务调用](../../../../../../packages/task-engine/src/bundle-engine.ts) | `invokeTask` 持久化父子组合关联，并等待子任务执行与释放 | 子任务默认拒绝，需宿主 `authorizeChild` 明确授权 |
| [server](../../../../../../packages/task-engine-server/README.md) | 程序化组装 HTTP/SSE；调用者负责信号与资源所有权 | 当前不提供 CLI；单次执行无需经由 HTTP |

`close()` 是主动关闭流程，可能终止尚未完成的工作，不是“先自然跑完队列”的代替。
Task 的逻辑终态、Run 的物理退出和资源回收是不同事实，不能只观察其中一个。

## “全部工作结束”的定义

这里的“队列清空”是业务工作耗尽，不是清空持久化数据库中的 Task/Run 历史。
本次根提交、其受支持的派生提交及为它们服务的在途工作均属于运行域。
默认使用独立运行域，避免历史待办和外部生产者不断加任务阻止退出。
存储后端、保留方式及将来的显式恢复模式，在实施时确定并写进帮助文档。

仅当以下工作都不存在时，才允许进入最终关闭：

1. 尚未给出 accepted/rejected 决定的 Request，包括等待获取 Bundle 的 preparation。
2. 尚未终结的 Task，包括待执行、等待执行资格或其他已受支持的等待状态。
3. 正在运行、停止处理或尚未确认物理退出的 Run。
4. 尚在提交、确认、等待结果或释放中的子任务调用，以及会继续产生本次工作的在途操作。
5. 尚未完成的资源回收；回收无法确认时必须明确失败，而不是报告正常耗尽。

这些条件必须来自一致的核心生命周期观察。不能依靠一次分页查询、
根任务 Promise 完成、执行池 `queued === 0`，或“连续一段时间没看到任务”来证明耗尽。
引擎自己的 tick、观察句柄等基础设施不算新的业务任务，但最终必须正常关闭。

## 派生任务与竞态

根任务运行中创建子任务，子任务又创建孙任务时，engine 必须覆盖整个有限闭包。
尤其需要证明以下顺序不会误退出：

```text
待执行队列暂时为零
  → 最后一个正在运行的任务提交子任务
  → 子 Request 等待 Bundle preparation
  → 父任务或观察者看到逻辑终态
  → 子任务进入运行并继续派生
  → 全部派生工作结束，完成物理回收
  → CLI 才退出
```

观察耗尽与最终停止之间，不能留出“已宣告耗尽，但仍允许在途提交产生遗漏任务”的窗口。
CLI 默认不开放外部提交入口；如果未来允许其他生产者，必须另行定义停止准入协议。

用户所说的 schedule 需与实际协议对齐。当前受支持的是结构化 `invokeTask`：
子任务关联有效父 Run，继承调用者身份，受父截止时间、深度、并发、总量及权限预算约束；
父结束或取消时，沿用既有子任务清理规则。
本 idea 不默认允许子任务脱离父生命周期继续后台执行，不放宽这些限制。
独立的 fire-and-forget schedule 若确有业务需求，需要另外定义持久关联、取消与恢复语义，
不能仅靠 CLI 多等一会儿就宣称支持。

## 等待、失败与中断

已受支持的未来执行资格不能因“现在没有可运行任务”而被忽略。
重试或其他延期状态若在实施时确认存在，同样必须计入未完成工作；
本 idea 不单独新增重试或周期调度能力。
无限派生、周期任务、永久业务等待可能永不自然耗尽，应清楚说明而非强行宣告完成。

有限任务失败也是终态。默认建议让其余仍有效的工作按现有生命周期处理，
最后汇总失败并返回非零退出码；不因为一项失败就偷偷改变现有取消规则。
父任务终结导致的子任务取消仍遵循已有组合语义。
整体最大运行时长如有必要应显式配置，达到上限应报告超时，而不是成功退出。

| 情况 | 对外结果要求 |
| --- | --- |
| 全部任务成功且清理确认 | 汇总成功并返回退出码 0 |
| 根提交拒绝或配置/输入无效 | 给出明确错误并返回非零退出码 |
| 任一应纳入结果的任务失败、停止或超时 | 汇总该终态，不伪装成功，返回非零退出码 |
| SIGINT/SIGTERM | 停止进一步工作并调用正常关闭流程，明确表示中断 |
| Worker/资源无法确认退出或回收 | 给出清理失败诊断，返回非零退出码 |

具体非零码分配、标准输出格式和诊断去向在实施阶段确定；
文档与测试必须对齐，不能把根任务成功当作整次执行成功。
不得用无条件 `process.exit(0)` 掩盖剩余句柄。
engine 不拥有共享 IPFS client 或独立内容节点，不能关闭共享节点或移除他人 pin；
由 CLI 创建且拥有的资源则必须释放。

## 可观察证明

实施验证至少覆盖以下风险，而不是只跑单任务 happy path：

- 单任务、并行子任务及多层派生均完整结束；空闲间隙不会提前退出。
- 最后一个任务在结束前提交子任务，子 Bundle 的获取被人为延迟。
- Task 已终态但 Worker 物理退出或资源释放被延迟，CLI 仍等待。
- 准入拒绝、子权限拒绝、任务失败、截止时间、中断和清理失败均明确非成功。
- 未来执行资格或其他现有等待状态仍保持运行；没有无限循环的正常完成承诺。
- 真实 CLI 子进程在工作结束并清理后自动退出，不靠测试进程强制杀掉来证明成功。
- 现有常驻 service 在空闲后继续可用，独立运行域不处理历史或无关任务。

## 实施前需定稿的接口细节

这些选择不得被本文的示意命令误当成已承诺的公共 API：

1. 耗尽观察接口名称、与停止准入的衔接以及错误传播方式。
2. CLI 包归属、CID/输入/Gateway/授权参数，以及独立存储域的生命周期。
3. 结果汇总、非零退出码、信号语义和可选整体时长预算。

这些实现选择应服务于上面的对外行为，不引入第二套 engine 或调度规则。
